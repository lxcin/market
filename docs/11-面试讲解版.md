# 11 · 面试讲解版

> 用法：先背「30 秒版」，再按主线讲；面试官往哪深挖，就用对应「亮点详解 + 追问 Q&A」。核心原则：**先给结论和数字，再讲方案和取舍。**

## 一、话术模板

### 30 秒版
> 我做过一个**在线书城**的单体后端（Spring Boot 3 + MySQL + Redis + ES），覆盖商品、购物车、下单、支付、优惠券秒杀、退款、后台。我重点做了三块：**高并发秒杀（压测零超卖）**、**分布式一致性（库存预占 + 本地消息表 + 延时关单 + 对账）**、**可观测性（指标/日志/链路/告警）**，并把支付做成了**验签回调 + 金额核对 + 幂等 + 对账**的生产级骨架。

### 2 分钟版
> 项目是 C 端书城，单体架构但一致性都按最终一致设计。技术上：Spring Boot 3.3 / MyBatis-Plus / MySQL / Redis + Redisson / Elasticsearch，安全用 Spring Security + JWT，可观测用 Micrometer + Prometheus + Grafana + Zipkin。
>
> 我承担了后端架构和核心编码。几个我做得比较深的点：
> 1. **秒杀**：把原来"分布式锁 + 查库扣减"改成 **Redis Lua 原子预扣 + Redis Stream 可靠队列 + 幂等落库 + 对账**，热路径不落库；自写压测脚本，1000 用户 / 500 并发 / 200 库存 → **成功恰好 200、零超卖**，QPS≈555、P99≈1s，三方数据完全一致。
> 2. **一致性**：下单用**库存预占**（预占→支付实扣→超时释放）+ **Outbox 本地消息表**（业务与事件同事务）+ **Redisson 延时队列**精确关单；再配**支付/库存/优惠券三处对账**。
> 3. **可观测**：指标 + traceId 日志 + Zipkin 链路 + 告警，重点解决了**异步回调/消费线程的链路上下文传播**。
> 也做过 ES 搜索（IK + 拼音 + 分面导航 + 别名零停机重建 + 降级）和安全加固（JWT 黑名单、越权修复、防重提交）。

## 三、亮点详解（每个都能讲 3-5 分钟）

### 亮点 1：秒杀零超卖
- **背景**：原实现是 Redisson 锁 + 查库限领 + DB `UPDATE remaining_count`，全串行在数据库，QPS 上不去；`seckill_claim.lua` 是死代码。
- **方案**：`Redis Lua` 一次 EVAL 内完成「库存判断 + DECR + 用户计数 + XADD 入队」，**原子且热路径不落库**；`Redis Stream` 消费组异步落库（唯一键幂等 + CAS 扣减 + PEL 重试）；启动预热库存，定时对账 `total/remaining/issued/Redis stock`。
- **为什么用 Redis Stream 不用 MQ**：本机 Docker 下 RocketMQ broker 广播容器内网 IP、宿主机不可达，而 Stream 零外部依赖即可提供**消费组 + PEL + 重试**。
- **数字**：1000 用户 / 500 并发 / 200 库存 → 成功 **200**（=库存）、失败 800；QPS≈555、P99≈1s；落库=200、remaining=0、Redis stock=0、pending=0。
- **坑**：Lua 里入队字段要带 `traceId/spanId` 供异步链路续接；`increase` 用户计数要带 TTL。

### 亮点 2：分布式一致性与支付
- **库存预占**：`t_inventory.locked_stock` 启用；下单 `reserveStock`（乐观锁 CAS），支付 `commitStock`，取消/超时 `releaseStock`，退款 `increaseStock`。**不变量**：`locked_stock == Σ待支付订单数量`。
- **Outbox**：`OrderServiceImpl` 在 `@Transactional` 内写订单 + 预占 + `t_outbox(ORDER_CREATED)`，独立投递器 2s 扫描 → 累加销量 + 刷新 ES；失败重试、超限置失败。
- **延时关单**：下单投递 `RDelayedQueue`（Redis ZSet，重启不丢），`OrderTimeoutConsumer` 专用线程 `take()` **阻塞消费**（零空转），到期 CAS 关单 + 释放库存 + 退券；保留 5min 低频兜底扫描。
- **支付**：模拟网关 RSA 签名，平台**公钥验签** + **金额三重核对** + **幂等 CAS** + 退款 + **对账补偿**。
- **数字**：库存对账 30 条 0 不一致；券对账 7 模板 0 不一致；outbox 事件全部 delivered；`stock 500→498/锁定2→支付后锁定0`。

### 亮点 3：可观测性 + 异步上下文传播
- 指标：Micrometer 自动埋点（HTTP/JVM/Hikari）+ 业务 Counter（下单/支付/秒杀/登录失败/对账差异）+ 缓存命中率。
- 日志：logback pattern 带 `traceId/spanId`（MDC）。
- 链路：Brave + Zipkin，`@Observed` 业务 span。
- **难点**：异步回调跑在 `pay-callback-*` 线程池、秒杀落库跑在消费线程，默认**断链**。解决：线程池挂 `ContextPropagatingTaskDecorator`；消息里透传 traceId/spanId 并构造子 span。结果：`sandbox→出站 client span→/notify→handle-notify` **同一条 12 span 的 trace**。
- 告警：Prometheus 规则（错误率/P95/登录失败/支付失败/抢完）+ Alertmanager，实测 `LoginFailureSpike` firing。

### 亮点 4：ES 搜索
- IK 中文分词 + `analysis-pinyin`（`周志华→zhouzhihua|zzh`）；字段检索（书名/作者/全部）+ 拼音 + 首字母；**分面导航**（筛选走 `post_filter`，聚合按候选集算）；高亮；**搜索建议**；**作者主页**；**版本化索引 + 别名零停机重建**；ES 挂了降级 MySQL 加权查询。
- 坑：强类型反序列化失败 → 用 `Map`；数值聚合是 `lterms`；别名不能在建索引时挂。

### 亮点 5：缓存三件套
- 两级缓存（本地 + Redis）+ 布隆防穿透 + Redisson 互斥锁防击穿 + 随机 TTL 防雪崩；命中率打点。

### 亮点 6：安全
- JWT + Redis 黑名单（登出/强制失效）、登录失败锁定、图形/短信验证码、BCrypt、越权（IDOR）修复、`@RepeatSubmit` 防重、方法级 `@PreAuthorize`、脱敏、CORS 白名单。

## 四、高频追问 Q&A

**Q：怎么保证不超卖？**
A：三道防线——Redis Lua 原子 DECR 是主闸；DB 侧 `t_user_coupon` 唯一键保证一人一券；对账校验 `issued == total - remaining` 与 Redis 库存。DB 层扣减用 `WHERE stock>=q AND version=?` 乐观锁。

**Q：Redis 扣了但落库失败怎么办？**
A：不会丢。消息进了 Redis Stream（持久化 AOF），消费失败留在 PEL，`XAUTOCLAIM` 重试；异常消息/漂移由对账发现。

**Q：为什么用 Outbox 不用事务消息？**
A：事务消息要 MQ（本项目 MQ 不可用）。Outbox 只用本地库就能保证"业务+事件"同事务原子，投递器异步消费，等价效果、零额外中间件。

**Q：为什么要库存预占，不直接扣？**
A：直接扣会让未支付订单长期占库存且无法区分"已售/被占"。预占把"占用"和"成交"分开，超时能释放，且给了可对账的不变量。

**Q：延时队列可靠吗？重启会丢单吗？**
A：元素在 Redis ZSet，重启不丢；消费端 `take()` 阻塞消费；再加每 5 分钟兜底扫描防极端丢失。

**Q：Mock 支付是不是玩具？**
A：不是。模拟的只是**第三方网关那一侧**；平台侧（验签、金额核对、幂等记账、回调、退款、对账）是按生产写的。上线只需替换网关实现 + 用配置加载网关公钥，其余不动。

**Q：为什么不上微服务？**
A：当前是个人项目、单体优先，能快速闭环；但一致性方案（Outbox/预占/对账/幂等键）正是为拆分准备的基础设施。要拆就是按领域拆 + 网关 + 配置中心 + Saga/TCC。

**Q：为什么用 Redis Stream 不用 Kafka？**
A：秒杀/购物车这种"可靠但量不大"的场景，Stream 零额外部署即可给消费组+PEL；Kafka 更重，等量级上来或跨服务再引入。

**Q：异步链路的 traceId 怎么保证不断？**
A：两处：线程池用 `ContextPropagatingTaskDecorator` 传播 TraceContext；跨 Redis Stream 用消息字段透传 traceId/spanId，消费端构造子 span 续接。

**Q：界面/越权这种问题怎么发现和修的？**
A：做权限自查时发现订单接口只查 `id` 不校验归属（IDOR），改成校验 `order.userId == 当前用户`，管理员查看走 admin 接口，并加方法级 `@PreAuthorize` 做纵深防御。

**Q：数据一致性怎么持续保证，而不是一次性的？**
A：定时对账（支付/库存/券）+ 指标 `business_reconcile_mismatch_total` + 告警规则，把"漂移"变成可观测、可告警的事件。

**Q：性能瓶颈在哪，怎么优化？**
A：压测显示 QPS≈550、P50 偏高，瓶颈是单机 Tomcat 线程数(200) + 瞬时全量请求 + 链路埋点开销。优化：调大线程/连接池、降低 tracing 采样、热点路径减埋点、水平扩容。

## 五、可能的"刁难"与应答

- **"这些不都是框架自带的吗？"** → 指标/JWT 是框架自带，但**秒杀预扣、Outbox、预占、延时关单、对账、异步链路续接**是业务设计，框架不提供。
- **"你只是调包吧？"** → 底层（Redis/Lucene/Spring）是调包，但**选型、模型设计（不变量/状态机）、异常与一致性处理**才是工程含量；比如别名零停机重建、post_filter 分面、PEL 重试都是设计取舍。
- **"数据是造的吧？"** → 有可复现的**压测脚本和一致性校验 SQL**，结果可复跑。
- **"没做过线上？"** → 坦白是个人项目，但按生产思路做了可观测、对账、降级、安全；缺少的是真实流量、多机房、SRE 流程。
